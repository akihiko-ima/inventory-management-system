# ペルソナ定義書

## 1. 本書の目的

本書は、在庫管理システムの追加機能を検討するにあたり、想定顧客(依頼者)の人物像・業務・要求・制約を定義する。
以降のプロダクト要求定義書(PRD)、機能設計書、アーキテクチャ設計書は、本書のペルソナを判断基準として作成する。

> 本書の人物・組織は想定上のものであり、実在の人物・組織とは関係ない。

---

## 2. ペルソナ概要

| 項目         | 内容                                                                                                          |
| ------------ | ------------------------------------------------------------------------------------------------------------- |
| 名前(仮)     | A さん                                                                                                        |
| 所属         | 地域密着型の小売業(数店舗規模)の本部                                                                          |
| 役割         | 店舗運営・商品管理の責任者。社内システムの窓口も兼任                                                          |
| ITリテラシー | 中〜高。FastAPI Full Stack Template の存在と構成(FastAPI / React / PostgreSQL / Docker Compose)を把握している |
| 開発体制     | 社内に専任エンジニアはいない。開発・保守は少人数の外部委託を想定                                              |
| 予算         | 限定的。ライセンス費用・SaaS 月額費用を継続的に払う余裕はすくない                                             |

### 2.1 一言で表すと

「FastAPI テンプレートをベースに、**OSS だけで**、**止まらず安全な**在庫・売上管理を手に入れたい人」

## 3. 業務と課題

### 3.1 抱えている業務

| 業務           | 内容                                                                        |
| -------------- | --------------------------------------------------------------------------- |
| 商品の売上集計 | 店舗別・商品別・期間別(日次 / 月次)に売上を集計し、販売動向を把握する       |
| 在庫管理       | 商品ごとの現在庫数を把握し、欠品・過剰在庫を防ぐ                            |
| 発注管理       | 在庫の減り具合を見て仕入先へ発注し、発注状況(発注済み / 入荷済み)を追跡する |
| 履歴の確認     | どの商品がいつ・いくつ売れたか、いつ・いくつ入荷したかを後から確認する      |
| 売上分析       | 月次・年間・店舗別の売上合計や、商品ごとの売れ行きの傾向を把握する          |

### 3.2 現状の課題(想定)

- 売上と在庫の情報が別々に管理されており、集計に手作業が発生している
- レジでの販売が在庫数に即時反映されないため、実在庫とシステム上の在庫がずれる
- 発注のタイミングが担当者の経験と勘に依存している
- 在庫切れに気づくのが遅れ、気づいたときには欠品している
- 商品名だけでは似た商品を見分けにくく、登録・棚卸のときに取り違えが起きる
- 商用パッケージは機能過多かつ高価で、導入・維持のコストが見合わない

## 4. ペルソナが求めていること

### 4.1 機能面の要求

| ID  | 要求                                                                                       | 優先度   | 備考                                                    |
| --- | ------------------------------------------------------------------------------------------ | -------- | ------------------------------------------------------- |
| F-1 | 商品マスタ(商品名・SKU・価格など)と在庫数を登録・管理できる                                | 高       | 現状は未実装(5章参照)                                   |
| F-2 | 売上集計画面で、月次・年間の売上、店舗別の売上合計を確認できる                             | 高       | 本部は全店舗の合計と店舗ごとの内訳を比較したい          |
| F-3 | 在庫の発注を登録し、発注〜入荷までの状況を管理できる                                       | 高       | 入荷時に在庫数へ加算                                    |
| F-4 | レジから API 経由で「どの商品が何個売れたか」を受け取り、在庫を自動で減らせる              | 中(将来) | 今後の構想。認証・認可が前提(4.3参照)                   |
| F-5 | 商品を見分けやすくするため、商品の写真を登録・差し替え・削除できる                         | 中       | 写真は S3 互換のオブジェクトストレージに保存する(4.4参照) |
| F-6 | 在庫が商品ごとに設定したしきい値を下回ったら、Slack に通知する                            | 中       | 通知は失敗しても再送され、取りこぼさないこと(4.4参照)   |
| F-7 | 店舗ごとに在庫を管理し、利用者は所属する店舗のデータにだけアクセスできる                   | 高       | データモデルの土台に関わるため初期から(4.4参照)         |
| F-8 | 商品ごとの販売・入荷の履歴(いつ・どの店舗で・いくつ)を一覧で確認できる                      | 高       | 在庫数の増減の根拠を後から追えるようにする              |
| F-9 | 商品の売れ行きのトレンド(期間ごとの推移、よく売れる / 売れない商品)を分析できる画面がある | 中       | F-2 の集計画面と合わせて提供したい                      |
| F-10 | 店舗間で在庫を移動できる                                                                  | 低       | F-7 の店舗単位の管理が前提                              |

### 4.2 予算・技術面の制約

- **OSS を前提とする**
  - 追加ライセンス費用が発生しないこと
  - 現行テンプレートの構成(FastAPI / SQLModel / PostgreSQL / React / Traefik / Docker Compose)をできる限り活かすこと
- **管理コストを抑える**
  - 少人数で運用・保守できる構成であること
  - 依存するミドルウェアや外部サービスをむやみに増やさないこと

### 4.3 非機能面の要求

ペルソナは予算を抑えたい一方で、「安くても止まる・漏れるシステムでは困る」と考えている。

#### (1) 可用性・拡張性

- 将来、**2台構成のホットスタンバイ**(アクティブ / スタンバイ)へ移行できるアーキテクチャであること
  - 初期は1台で運用しても構わないが、後から2台構成にする際に大きな作り直しが不要であること
  - 例: アプリケーションをステートレスに保つ、データベースのレプリケーションを前提にした設計にする
- 店舗数や取扱商品数が増えても対応できる拡張性があること

#### (2) セキュリティ

- 昨今話題になっているセキュリティリスクに対して、安心できる仕組みがあること
  - 例: ランサムウェア、不正アクセス、サプライチェーン攻撃(OSS 依存パッケージの脆弱性・改ざん)
- 期待する観点(例)
  - 依存パッケージの脆弱性を継続的に検知・更新できる仕組み
  - 通信の暗号化(HTTPS)
  - 操作・アクセスの監査ログ
  - バックアップと復旧手順(ランサムウェア対策を含む)
  - 権限の最小化(必要な人・機器に必要な操作だけを許可する)
  - **店舗間のデータ分離をデータベースの仕組みで保証する**こと
    - アプリケーションのコードに不具合があっても、他店舗のデータが見えてしまわないようにしたい
    - PostgreSQL の行レベルセキュリティ(RLS)で店舗ごとの分離を担保する

#### (3) レジ連携の認証・認可

- レジからのリクエストは**店内からの通信であっても**、認証・認可の仕組みを必須とする
  - 「社内ネットワークだから安全」という前提には立たない
  - レジ端末ごとに識別でき、不正な端末や漏えいした認証情報を個別に無効化できること
  - レジ端末には「販売の登録」など必要最小限の操作だけを許可し、商品マスタの変更やユーザー管理はできないこと

### 4.4 要求の実装イメージ(ヒアリング時点の仮説)

ペルソナとの会話で出た実装の方向性を記録する。確定ではなく、アーキテクチャ設計書(`docs/architecture.md`)で 4.2 の制約(OSS 前提・管理コスト)と照らして最終判断する。

| 関連要求  | 実装イメージ                                                                                                                                                  | 検討ポイント                                                                                                                       |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| F-7       | 店舗をテナントとみなした**マルチテナント構成**。1つのデータベースを共有し、各テーブルに店舗 ID を持たせる。分離は PostgreSQL の **RLS** で強制する            | **テナント = 店舗**とする(ペルソナと合意済み)。本部ユーザーは全店舗を横断して閲覧する必要があるため、RLS で横断アクセスをどう許可するかを決める |
| F-5       | 写真は **S3 互換のオブジェクトストレージ**に保存し、DB には参照(キー)だけを持つ。開発環境では S3 のダミーとして **RustFS** などの OSS を Docker Compose で動かす | 本番も OSS(セルフホスト)にするか、クラウドの S3 にするか。2台構成時の共有・冗長化とバックアップの方法                               |
| F-6       | 在庫しきい値の判定と Slack 通知を**バックグラウンドジョブ**で処理する。キューに **Redis + RQ** などを使い、**リトライ**と**デッドレターキュー**を備える      | Kafka は運用負荷が高く、4.2「ミドルウェアをむやみに増やさない」とのバランスから Redis + RQ が有力。通知先は Slack Incoming Webhook を想定 |
| F-2 / F-9 | 販売・入荷の履歴(F-8)を集計元にして、月次・年間・店舗別の集計とトレンドをグラフで表示する                                                                   | データ量が増えたときの集計性能(集計用のビューやテーブルを持つか)                                                                   |

## 5. 現状システムとの差分

依頼時点では「在庫の登録機能のみがある」との認識だったが、コードを確認した結果、**在庫の登録機能はまだ存在しない**。
現状は FastAPI Full Stack Template の初期状態であり、主な機能は以下のとおり。

| 区分           | 現状                                                                                     | ペルソナの要求とのギャップ                                           |
| -------------- | ---------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| データモデル   | `User` と `Item` のみ。`Item` は `title`(名称)と `description`(説明)だけを持つ汎用モデル | 在庫数・SKU・価格・店舗などの項目がない。売上・発注のモデルもない    |
| 機能           | ユーザー登録・ログイン・パスワード再設定、`Item` の CRUD、管理者によるユーザー管理       | 在庫管理・売上集計・発注管理が未実装                                 |
| データの見え方 | 一般ユーザーは自分が作成した `Item` だけを閲覧・編集できる                               | 店舗やチームで在庫を共有する考え方がない                             |
| 認証           | ユーザー向けの JWT(HS256、有効期限8日)によるログイン                                     | レジ端末のような機器向けの認証手段がない                             |
| 認可           | 一般ユーザー / スーパーユーザーの2段階のみ                                               | 役割(店舗スタッフ・本部・レジ端末など)ごとの細かい権限制御がない     |
| 構成           | Docker Compose による1台構成(Traefik / PostgreSQL / Backend / Frontend)                  | 2台ホットスタンバイ、DB レプリケーション、バックアップの仕組みがない |
| ファイル保存   | 画像などのファイルをアップロード・保存する仕組みがない                                   | 商品写真の保存先・配信方法・バックアップを新たに用意する必要がある   |
| データ分離     | 店舗やテナントの概念がなく、RLS も使っていない                                           | 店舗単位のアクセス制御と、DB レベルでの分離の仕組みがない            |
| 非同期処理     | バックグラウンドジョブやキューの仕組みがない(メール送信も同期処理)                       | 通知のリトライ・デッドレターキューを含むジョブ基盤がない             |
| 外部通知       | メール送信(SMTP)のみ                                                                     | Slack への通知手段がない                                             |
| 集計・分析画面 | なし                                                                                     | 売上集計・トレンド分析の画面がない                                   |

## 6. 成功の定義(ペルソナ視点)

- 売上と在庫が1つのシステムでつながり、集計の手作業がなくなる
- 在庫数を見て、適切なタイミングで発注できる
- 在庫がしきい値を下回ったら Slack で気づけ、欠品を防げる
- 写真付きで商品を見分けられ、取り違えが減る
- 月次・年間・店舗別の売上とトレンドを画面で確認でき、仕入れや販促の判断に使える
- 各店舗のスタッフは自店舗のデータだけを扱え、他店舗のデータが漏れない
- 追加のライセンス費用をかけずに運用できる
- 1台が故障しても、もう1台に切り替えて業務を続けられる見通しが立っている
- レジ連携を含め、「誰が・どの端末が・何をしたか」を把握でき、不正を防げる
