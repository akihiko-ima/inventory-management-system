# プロダクト要求定義書 (Product Requirements Document)

> 本書は `docs/persona.md`(ペルソナ定義書)を入力として作成する。要求 ID(F-1 など)はペルソナ定義書 4.1 と対応する。

## プロダクト概要

### 名称

**在庫・売上管理システム(仮称)** - 複数店舗を持つ小規模小売業向けの、OSS だけで運用できる在庫・売上管理 Web アプリケーション

### プロダクトコンセプト

- **在庫と売上を1つにつなぐ**: 販売・入荷の記録がそのまま在庫数と売上集計に反映され、手作業の集計をなくす
- **店舗ごとに安全に分ける**: 店舗をテナントとし、データベースの行レベルセキュリティ(RLS)で店舗間のデータ分離を保証する
- **安く、止まらず、漏れない**: OSS と既存の FastAPI Full Stack Template を活かし、ライセンス費用ゼロのまま 2 台構成・セキュリティ対策へ拡張できる

### プロダクトビジョン

数店舗規模の小売業が、高価な商用パッケージに頼らずに、店舗ごとの在庫・発注・売上を1つのシステムで把握できるようにする。
在庫が減れば Slack で知らせ、写真付きの商品マスタで取り違えを防ぎ、月次・年間・店舗別の売上とトレンドを画面で確認できる。
専任エンジニアのいない組織でも少人数で運用でき、将来の 2 台構成やレジ連携に作り直しなしで進める土台を提供する。

### 目的

- 売上と在庫の情報を一元化し、売上集計の手作業をなくす
- 在庫の減少を早期に知らせ、欠品を防ぐ
- 店舗ごとのデータを、アプリケーションの不具合があっても漏れない形で分離する
- 追加のライセンス費用・SaaS 月額費用なしで運用できる構成にする

## ターゲットユーザー

### プライマリーペルソナ: A さん(本部の店舗運営・商品管理責任者)

- 地域密着型の小売業(数店舗規模)の本部に所属し、社内システムの窓口も兼任している
- IT リテラシーは中〜高。FastAPI / React / PostgreSQL / Docker Compose の構成を把握している
- 社内に専任エンジニアはおらず、開発・保守は少人数の外部委託を想定。予算は限定的
- **現在の課題**
  - 売上と在庫が別々に管理され、店舗別・期間別の集計を手作業で行っている
  - 在庫切れに気づくのが遅れ、発注タイミングが担当者の経験と勘に頼っている
  - 商品名だけでは似た商品を見分けにくく、登録・棚卸で取り違えが起きる
- **期待する解決策**: 全店舗の在庫・売上を1画面で見渡し、在庫が減ったら通知で気づき、数字に基づいて発注できる
- **典型的なワークフロー**
  1. 朝、Slack の在庫アラートを確認し、しきい値を下回った商品を発注する
  2. 日中、入荷した発注の入荷処理を行い、在庫数を更新する
  3. 月初に月次の売上を店舗別に確認し、売れ筋・不振商品を把握して仕入れを判断する

### セカンダリーペルソナ: 店舗スタッフ

- 各店舗に所属し、自店舗の販売・入荷・在庫確認を担当する
- 他店舗のデータを見る必要はなく、見えてはならない
- 写真を見て商品を確認しながら作業したい

### 利用者の役割

| 役割                 | 説明                                                         | アクセス範囲                   |
| -------------------- | ------------------------------------------------------------ | ------------------------------ |
| システム管理者       | ユーザー・店舗の管理を行う(テンプレートのスーパーユーザー) | 全店舗・全機能                 |
| 本部ユーザー         | 商品マスタの管理、全店舗の在庫・発注・売上の閲覧と操作       | 全店舗(横断)                 |
| 店舗スタッフ         | 自店舗の販売・入荷・在庫の操作と閲覧                         | 所属店舗のみ                   |
| レジ端末(P1 で追加) | 販売の登録のみ                                               | 設置された店舗の販売登録のみ   |

## 成功指標(KPI)

> 現時点で現状値の計測データはないため、目標値は仮置きとする。運用開始前に現状値を計測し、目標値を確定する。

### プライマリーKPI

- **月次売上集計にかかる作業時間**: 運用開始後 3 ヶ月で、現状比 90% 以上削減(画面表示のみで完結)
  - 測定方法: 運用開始前に A さんの月次集計作業時間を記録し、運用開始 3 ヶ月後と比較する
- **欠品発生件数**: 運用開始後 6 ヶ月で、運用開始前の同期間比 50% 削減
  - 測定方法: 在庫数が 0 になった「商品 × 店舗」の件数を在庫履歴から集計する
- **在庫しきい値アラートの通知成功率**: 99% 以上(リトライ後の最終結果で測定、常時)
  - 測定方法: 通知ジョブのうち、デッドレターキューに入らずに送信完了した割合

### セカンダリーKPI

- **棚卸時の在庫差異率**(システム在庫と実在庫の差): 運用開始後 6 ヶ月で 2% 以下
- **店舗間のデータ漏えい件数**: 0 件(常時。RLS の自動テストと監査ログで確認)
- **追加ライセンス費用・SaaS 月額費用**: 0 円(常時)

### コア機能(MVP)

#### 1. 店舗管理とアクセス分離(F-7)

**ユーザーストーリー**:
本部ユーザーとして、店舗ごとに在庫を正しく管理し他店舗のデータ漏えいを防ぐために、店舗を登録し、利用者を店舗に所属させたい

**受け入れ条件**:

- [ ] システム管理者が店舗(店舗名・店舗コード・住所)を登録・編集・無効化できる
- [ ] システム管理者がユーザーに役割(本部ユーザー / 店舗スタッフ)と所属店舗を設定できる
- [ ] 店舗スタッフは、画面・API のどちらからも所属店舗のデータだけを閲覧・操作できる
- [ ] 本部ユーザーは全店舗のデータを横断して閲覧でき、店舗を指定して絞り込める
- [ ] 店舗間の分離は PostgreSQL の RLS で強制され、アプリケーションのクエリに店舗条件が抜けていても他店舗の行は返らない
- [ ] 他店舗のデータへのアクセスを試みた場合、存在しないものとして扱われる(404)

**優先度**: P0(必須)

#### 2. 商品マスタと在庫管理(F-1)

**ユーザーストーリー**:
本部ユーザーとして、全店舗で同じ商品を同じ基準で扱うために、商品マスタを登録し、店舗ごとの在庫数を管理したい

**受け入れ条件**:

- [ ] 本部ユーザーがカテゴリ(マスタ)を登録・編集・無効化でき、商品はカテゴリを選択して登録する
- [ ] 本部ユーザーが商品(商品名・SKU・販売価格・カテゴリ・説明)を登録・編集・無効化できる
- [ ] SKU はシステム内で一意であり、重複登録はエラーになる
- [ ] 商品マスタは全店舗で共通。在庫数は「商品 × 店舗」ごとに管理される
- [ ] 在庫一覧を店舗・商品名・SKU・カテゴリで検索・絞り込みでき、在庫数で並べ替えられる
- [ ] 在庫数は販売・入荷・棚卸調整によってのみ変化し、直接書き換えることはできない
- [ ] 棚卸調整では、調整後の数量と理由を入力し、差分が履歴に残る
- [ ] 画面からの操作(販売・棚卸調整)で在庫数がマイナスになる場合はエラーになる。レジからの販売(機能10)だけはマイナス在庫を許し、棚卸調整で正す

**優先度**: P0(必須)

#### 3. 販売の登録(F-2 / F-8 の前提)

**ユーザーストーリー**:
店舗スタッフとして、売上と在庫を一致させるために、販売した商品と数量を登録したい

**受け入れ条件**:

- [ ] 店舗スタッフが自店舗の販売(商品・数量・販売日時・販売単価)を画面から登録できる
- [ ] 1 回の登録で複数商品をまとめて登録できる
- [ ] 販売を登録すると、同じトランザクションで該当店舗の在庫数が減る
- [ ] 販売単価の初期値は商品マスタの販売価格で、登録時に変更できる(値引き対応)
- [ ] 誤登録は「取消」として登録し、在庫を戻す。元の販売記録は削除しない

**優先度**: P0(必須)

> レジからの自動登録は「10. レジ連携」(P1)で扱う。MVP では画面からの手入力とする。

#### 4. 発注・入荷管理(F-3)

**ユーザーストーリー**:
本部ユーザーとして、欠品を防ぐために、店舗ごとの発注を登録し、入荷までの状況を追跡したい

**受け入れ条件**:

- [ ] 本部ユーザー・店舗スタッフが、店舗・仕入先・商品・数量を指定して発注を登録できる
- [ ] 発注のステータスは「発注済み → 一部入荷 → 入荷済み」と遷移し、入荷済みになる前であれば「取消」にできる
- [ ] 1 つの発注に対して入荷を複数回に分けて登録できる(分納)
- [ ] 入荷処理を行うと、同じトランザクションで該当店舗の在庫数が入荷数量分増える
- [ ] 発注数量と入荷数量が異なる場合、実際の入荷数量を入力できる。残数が届かない場合は、発注を「入荷済み」として締められる
- [ ] 発注一覧をステータス・店舗・期間で絞り込める
- [ ] 仕入先(名称・連絡先)を登録・編集できる

**優先度**: P0(必須)

#### 5. 在庫の入出庫履歴(F-8)

**ユーザーストーリー**:
本部ユーザーとして、在庫数の増減の根拠を後から確かめるために、商品ごとの販売・入荷・調整の履歴を見たい

**受け入れ条件**:

- [ ] 在庫が変化するすべての操作(販売・販売取消・入荷・棚卸調整)が履歴として記録される
- [ ] 履歴には日時・店舗・商品・区分・増減数・操作後の在庫数・操作者が含まれる
- [ ] 履歴を商品・店舗・区分・期間で絞り込んで一覧表示できる
- [ ] 履歴は追記のみで、画面・API から編集・削除できない
- [ ] 履歴の在庫増減を合計すると、現在の在庫数と一致する

**優先度**: P0(必須)

#### 6. 売上集計画面(F-2)

**ユーザーストーリー**:
本部ユーザーとして、仕入れや販促の判断をするために、月次・年間・店舗別の売上を画面で確認したい

**受け入れ条件**:

- [ ] 指定した年の月次売上(売上金額・販売数量)を表とグラフで表示できる
- [ ] 年間売上を年ごとに表示し、前年と比較できる
- [ ] 店舗別の売上合計を表示し、全店舗合計と店舗ごとの内訳を比較できる
- [ ] 期間・店舗・カテゴリで絞り込める
- [ ] 店舗スタッフが開いた場合は、所属店舗の売上だけが表示される
- [ ] 売上金額は「販売数量 × 販売単価」の合計(取消分を除く)で算出する

**優先度**: P0(必須)

### MVP 後に追加する機能

#### 7. 商品写真の管理(F-5)

**ユーザーストーリー**:
店舗スタッフとして、似た商品を取り違えないために、商品の写真を見ながら作業したい

**受け入れ条件**:

- [ ] 本部ユーザーが商品ごとに写真を登録・差し替え・削除できる
- [ ] 対応形式は JPEG / PNG / WebP、1 枚あたり 5MB まで。形式・サイズ違反はエラーになる
- [ ] 商品一覧・在庫一覧・販売登録画面にサムネイルを表示する
- [ ] 写真は S3 互換のオブジェクトストレージに保存し、データベースには参照(キー)だけを保存する
- [ ] 開発環境では S3 互換の OSS(RustFS など)を Docker Compose で起動して利用できる
- [ ] 写真を差し替え・削除したとき、古いファイルがストレージに残り続けない

**優先度**: P1(重要)

#### 8. 在庫しきい値の Slack 通知(F-6)

**ユーザーストーリー**:
本部ユーザーとして、欠品する前に発注するために、在庫がしきい値を下回ったら Slack で知らせてほしい

**受け入れ条件**:

- [ ] 「商品 × 店舗」ごとに在庫のしきい値を設定できる(未設定の場合は通知しない)
- [ ] 販売・棚卸調整で在庫がしきい値を下回ったとき、Slack に通知する(店舗名・商品名・SKU・現在庫数・しきい値を含む)
- [ ] 通知はバックグラウンドジョブで送信し、販売登録などの画面操作の応答を遅らせない
- [ ] 送信に失敗した場合、間隔を空けて最大 5 回まで自動で再送する
- [ ] 再送しても失敗したジョブはデッドレターキューに移し、管理者が一覧で確認して再実行できる
- [ ] しきい値を下回り続けている間、同じ「商品 × 店舗」について重複通知しない(しきい値以上に戻った後に再び下回ったら再度通知する)
- [ ] しきい値を下回っている「商品 × 店舗」の一覧を画面で確認できる

**優先度**: P1(重要)

#### 9. 売上トレンド分析画面(F-9)

**ユーザーストーリー**:
本部ユーザーとして、売れ筋・不振商品を把握して仕入れを最適化するために、商品の売れ行きの推移を分析したい

**受け入れ条件**:

- [ ] 指定期間の売上上位・下位の商品ランキング(売上金額・販売数量)を表示できる
- [ ] 商品・カテゴリを指定して、日次・週次・月次の売上推移を折れ線グラフで表示できる
- [ ] 店舗を指定して、または全店舗で比較できる
- [ ] 指定期間に一度も売れていない商品を一覧表示できる

**優先度**: P1(重要)

#### 10. レジ連携(F-4)

**ユーザーストーリー**:
店舗スタッフとして、販売の手入力をなくし在庫を即時に正しく保つために、レジで売れた商品と数量が自動で登録されてほしい

**受け入れ条件**:

- [ ] レジから API 経由で販売(商品の SKU・数量・販売単価・販売日時)を登録でき、画面からの販売登録と同じく在庫が減り、履歴に残る
- [ ] 在庫が不足していても、レジからの販売は拒否せずに登録する(実際に商品は売れているため)。マイナスになった在庫は画面で分かるように表示し、棚卸調整で正す
- [ ] システム管理者がレジ端末を店舗に紐づけて登録し、端末ごとに認証情報を発行できる
- [ ] 店内からの通信であっても、認証情報のないリクエストは拒否する
- [ ] 端末ごとに認証情報を無効化・再発行でき、無効化した認証情報は即時に使えなくなる
- [ ] レジ端末に許可する操作は「紐づいた店舗の販売登録」だけで、商品マスタの変更・他店舗の操作・ユーザー管理はできない
- [ ] 通信エラーでレジが同じ販売を再送しても、二重に登録されない(レジ側の取引 ID で重複を判定する)
- [ ] レジ端末からの登録は、端末を識別できる形で監査ログに記録される

**優先度**: P1(重要)

### 将来的な機能(Post-MVP)

#### 11. 店舗間の在庫移動(F-10)

ある店舗の在庫を別の店舗へ移動する。移動元の減少と移動先の増加を1つの操作として記録し、履歴に残す。

**優先度**: P2(できれば)

## 非機能要件

> 規模の前提: 店舗 20 店舗まで、商品 5,000 SKU まで、販売明細 年間 100 万件まで、同時利用者 50 人まで

### パフォーマンス

- 一覧・登録・更新 API の応答時間: 95 パーセンタイルで 500ms 以内
- 売上集計画面・トレンド分析画面: 3 年分のデータを対象に 3 秒以内に表示
- 在庫しきい値の Slack 通知: しきい値を下回る操作から 1 分以内に送信(Slack 側の障害時を除く)
- 写真のアップロード: 5MB の画像で 5 秒以内に完了(店舗の一般的な回線で)

### ユーザビリティ

- 店舗スタッフが、30 分の説明で販売登録・入荷処理・在庫確認を行えるようになる
- 主要画面(在庫一覧・販売登録・入荷処理・売上集計)へ、ログイン後 2 クリック以内で到達できる
- PC とタブレット(横幅 768px 以上)で操作できる
- エラーメッセージは日本語で、原因と対処が分かる内容にする

### 信頼性・可用性

- 在庫数の更新と履歴の記録は同じトランザクションで行い、どちらか一方だけが反映されることはない
- データベースのバックアップを 1 日 1 回以上取得し、30 日分を保持する。写真もバックアップ対象に含める
- バックアップの少なくとも 1 世代は、本番環境から書き換え・削除できない場所に保管する(ランサムウェア対策)
- バックアップからの復旧手順を文書化し、半年に 1 回以上、復旧訓練を行う
- アプリケーションはステートレスに保ち(セッション・ファイルをローカルに持たない)、将来 2 台構成のホットスタンバイ(アクティブ / スタンバイ)に作り直しなしで移行できる
- 2 台構成への移行後の目標: 1 台の故障から 30 分以内に業務を再開できる

### セキュリティ

- 店舗間のデータ分離を PostgreSQL の RLS で強制し、店舗スタッフが他店舗のデータにアクセスできないことを自動テストで検証する
- すべての通信を HTTPS で暗号化する
- 役割(システム管理者・本部ユーザー・店舗スタッフ・レジ端末)ごとに、必要最小限の操作だけを許可する
- ログイン・データ変更・権限変更の操作を、操作者・日時・対象とともに監査ログに記録し、1 年間保持する
- 依存パッケージ(Python・npm・コンテナイメージ)の脆弱性を CI で継続的に検知し、重大な脆弱性は検知から 2 週間以内に更新する
- Slack の Webhook URL・ストレージの認証情報などの秘密情報は、ソースコードに含めず環境変数で管理する
- 写真のアップロードはファイル形式を内容で検証し、画像以外のファイルを受け付けない

### スケーラビリティ

- 店舗の追加は画面からの登録だけで行え、コードや設定の変更を必要としない
- 規模の前提(店舗 20・商品 5,000 SKU・販売明細 年間 100 万件)の 2 倍までは、構成を変えずにパフォーマンス要件を満たす

### 運用・コスト

- 利用するソフトウェアはすべて OSS とし、追加のライセンス費用・SaaS 月額費用を発生させない(Slack は依頼者が既に利用しているワークスペースを使う)
- 追加するミドルウェアは、オブジェクトストレージとジョブキュー(Redis など)にとどめる
- Docker Compose で全構成を起動でき、少人数で運用・保守できる

## スコープ外

明示的にスコープ外とする項目:

- 複数の会社(法人)をまたぐマルチテナント。本システムのテナントは「店舗」であり、1 社での利用を前提とする
- 会計・経理(仕訳・請求書発行・税計算)
- 顧客管理・ポイント管理
- EC サイトとの連携
- 需要予測・自動発注(発注の判断は人が行う)
- 仕入先へ発注書を自動送信する機能
- Slack 以外の通知チャネル(メール・LINE など)
- スマートフォン向けの専用アプリ
